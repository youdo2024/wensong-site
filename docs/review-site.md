# 審核用測試站

觸發指令：**「開審核測試站」**。

給金流／審核單位看的站。外觀與正式站一模一樣，只有拿到帳密的人進得來，
而且所有「會對外造成後果」的行為都被程式強制關掉。

正式站完全不受影響：`REVIEW_SITE` 沒設就是現在的行為，一行邏輯都不會走到。

---

## 為什麼要整站擋，不能用網址金鑰

2026-08-13 審核人員的原話：「我按到首頁還是會出現」。

用網址參數當預覽金鑰（`/api/shop-preview?k=…`）只擋得住那一頁，
擋不住從那一頁點出去的整個網站。要嘛整站擋，要嘛等於沒擋。

Basic Auth 擋在 middleware，**包含 `/api` 與圖片**。門開著只鎖客廳沒有意義。

---

## 四道強制保險

都只看環境變數，不吃資料庫設定，站長改不掉也忘不掉。

| # | 保險 | 為什麼 |
|---|---|---|
| 1 | 發票一律走光貿測試環境 | 2026-08-13 審核人員在正式站測試下單，光貿真的開出正式發票 DR69013737，站長事後手動作廢。**就算把正式金鑰貼進測試站也開不出正式發票**（實測過） |
| 2 | 所有信改寄 `REVIEW_MAIL_TO` | 審核人員下的測試單不會寄信給真實顧客，也不會把夥伴叫起來出貨。沒設就整個不寄 |
| 3 | GA 與 Meta 像素關閉 | 測試流量不混進正式數據，不污染廣告受眾 |
| 4 | 全站 noindex | 外觀跟正式站一樣，被索引就是整站重複內容，會傷正式站排名 |

## 兩個站怎麼分開：兩條 branch

```
main     →  正式站  www.wensong.tw      不設 REVIEW_SITE
review   →  審核站  review.wensong.tw   REVIEW_SITE=1
```

**為什麼要分 branch 而不是同一條靠環境變數切**：審核站要放的是「上線後的樣子」
（新方案頁、沒有支持字眼），正式站要維持「現在的樣子」（支持系統還在收錢）。
內容本來就不同，硬用 `if (isReviewSite())` 在程式裡到處切換，
一個判斷寫錯就是正式站跑出新方案頁。

分 branch 還有一個更重要的好處：**Zeabur 的正式站服務只監聽 `main`**，
所以在 `review` 上做的任何事，都不可能意外上到正式站。

### 平常怎麼走

| 你要做的事 | 推哪裡 |
|---|---|
| 修 bug、正式站的功能 | `main`，之後 `git merge main` 進 review 讓兩邊同步 |
| 審核用的新東西（方案頁、拿掉支持語言） | 只推 `review` |
| 審核通過，要上線 | `git merge review` 進 `main`，一次全部上線 |

### 一道你不可能搞錯的保險

middleware 會檢查「網域」與「REVIEW_SITE」是否一致，不一致就整站 503。

- `review.wensong.tw` 沒設 `REVIEW_SITE=1` → 503
- `www.wensong.tw` 誤設了 `REVIEW_SITE` → 503

為什麼寧可讓它整站掛掉：這兩種設定錯誤都是「靜靜地壞掉」。
審核站忘了設旗標，就變成一個公開的、會開正式發票、會寄真信給顧客的站，
而且外觀跟正式站一模一樣，點進去完全看不出問題。
正式站誤設旗標，則是所有顧客的信被改寄到同一個信箱、發票全變測試發票。
兩種都可能三天後才發現。503 你五分鐘內就知道。

本機預覽、IP、`*.zeabur.app` 不受這道檢查影響（只認結尾是 wensong.tw 的網域）。

## Zeabur 設定步驟

1. 在同一個專案裡**新增一個服務**，指向同一個 GitHub repo（`youdo2024/wensong-site`）
   　⚠️ **Branch 一定要選 `review`**，不是 main。同時去確認正式站那個服務的 branch 是 `main`
2. **掛一個新的 volume 到 `/app/data`**
   　⚠️ **絕對不能跟正式站共用**。共用的話審核人員的測試單會進正式訂單、扣正式庫存
3. 環境變數（密碼站長自己填，Claude 不經手）：

```
REVIEW_SITE=1

# 給審核單位的通行金鑰（一條連結點一次就好，之後不再跳任何框）
REVIEW_KEY=<一段長亂碼，用 openssl rand -hex 16 產>

# 舊的帳密方式仍然可用，但會跳瀏覽器登入框，不建議給審核人員
# REVIEW_USER=<審核單位的帳號>
# REVIEW_PASS=<審核單位的密碼>

# 給站長自己的（全站含後台）
REVIEW_ADMIN_USER=<你的帳號>
REVIEW_ADMIN_PASS=<你的密碼>

# 後台登入（一定要跟正式站不同：審核站的帳密會躺在對方的通訊軟體紀錄裡）
ADMIN_PASSWORD=<只給這台用的>
ADMIN_SECRET=<隨機字串，用 openssl rand -base64 32 產>

REVIEW_MAIL_TO=<你自己的信箱，測試站的信全部寄到這裡>
SITE_URL=https://review.wensong.tw
```

### 兩種開放方式，二選一

**（一）直接給網址（站長選的做法）**

```
REVIEW_OPEN=1
```

審核人員直接開 `https://review.wensong.tw` 就看得到，什麼都不用帶。
後台仍然要 Basic Auth——公開的是「像正式站的前台」，不是後台。

公開的代價與對應的補償：

| 風險 | 怎麼擋 |
|---|---|
| 搜尋引擎收錄成正式站的重複內容 | 全站 `noindex`＋`robots.txt` 整站 Disallow＋`sitemap.xml` 回空，三道 |
| 真客人誤入下單 | 信一律轉寄站長且主旨標「［測試站］」、發票強制測試環境，不會產生正式發票、不會通知夥伴出貨 |
| 有人刷到真錢 | **只要這台不設正式金流金鑰就不可能。開站前務必確認** |

最後那一列是唯一需要人確認的，另外兩列程式已經做完。

**（二）通行連結（比較保守）**

```
REVIEW_KEY=<一段長亂碼>
```

### 給審核人員的連結長這樣

```
https://review.wensong.tw/?rk=<REVIEW_KEY>
```

點一次，middleware 種一顆 90 天的 httpOnly cookie，**並立刻把金鑰從網址上抹掉**
（不要讓它留在對方的瀏覽紀錄或被順手轉貼出去），然後導回乾淨的首頁。
之後她怎麼逛都不會再看到任何登入框，體感就是一個正常的網站。

沒有通行證的人看到的是 **404**，不是登入框。回 401 等於昭告
「這裡有一個藏起來的站」，反而引人來試。

### 為什麼不乾脆完全公開

網路上會多出一個跟正式站一模一樣的問爽的。真的客人萬一走進來下單，
那筆單不會有人出貨——而他不會知道自己買錯地方。
一條連結的成本幾乎是零，換掉這個風險很划算。

### 為什麼要兩組身分

審核人員看的是前台，後台的存在對他沒有意義，也不該讓他知道。
拿通行連結進來的人存取 `/admin` 與 `/api/admin` 一律回 **404**——
不是 403。403 等於告訴對方「這裡有東西，只是你沒權限」，他就知道有後台可以試；
404 是這條路根本不存在，點來點去不會發現登入頁。

`REVIEW_ADMIN_USER` 沒設的話，後台對所有人都是 404（安全的預設值）。

這只是第一層，後台本身仍然要 `ADMIN_PASSWORD` 才登得進去。

### 關於 ADMIN_SECRET

它不是密碼，是拿來簽後台 cookie 的金鑰，你永遠不會手動輸入它。
只要夠長夠亂就好，在終端機打一行就有：

```
openssl rand -base64 32
```

正式站與審核站要各設一組不同的。共用的話，在審核站簽出來的後台 cookie
拿到正式站也會是有效的。改掉它的唯一後果是該站已登入的後台全部被登出。

4. **不要**設 `AMEGO_TAX_ID` / `AMEGO_APP_KEY`（設了也會被保險擋掉，但不設更乾淨）
5. 金流金鑰照審核需要設：TapPay 沙盒或正式，由站長決定
6. 綁一個網址，例如 `review.wensong.tw`，或直接用 Zeabur 給的 `*.zeabur.app`

## 資料要不要從正式站搬過去

不建議整包搬。測試站是空資料庫時，`lib/db.ts` 的種子會自動建出文章、商品、
捐贈碼清單，看起來就已經像一個完整的站。搬正式資料的話，
**顧客的姓名、電話、地址、Email 會整份複製到一個只有一道 Basic Auth 的機器上**，
那是拿真實個資去換一點點畫面真實度，不划算。

要幾筆訂單當樣本的話，在測試站自己下幾筆就好。
